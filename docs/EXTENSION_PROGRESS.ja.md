# 拡張機能の実装 — P2-01

[English](EXTENSION_PROGRESS.md)

## 実装した範囲

P2-01では `packages/extension` を追加しました。TypeScript製のVS Code拡張パッケージで、`*.png` に対して優先度 `option` でカスタムエディター `vectorPng.editor` を登録し、構造判定による起動分岐を行う `Vector PNG: Open in Editor` コマンドと、1024×1024の透過新規文書を作る `Vector PNG: New Document` を実装しています。通常PNGは標準画像ビューアーへ分岐し、破損したvector-pngは診断を表示します。判定では埋め込みSVGを解凍・解析・実行しません。本フェーズで登録するエディターは読み取り専用で、スクリプト禁止のWebviewに制限的なCSPを適用して保存済みPNGラスターを表示します。SVGをDOMへ挿入することはありません。

## 検証

Node 24の単体テストで、判定（通常PNG、有効なvector-png、誤ったテキストチャンク内のキーワード、ソースチャンクの重複、無圧縮ソース、CRC不良、切り詰め、非PNG）、4種の判定結果すべてに対する分岐、新規文書（寸法、全透過ラスター、埋め込みソースの往復）を検証し、ローカルで15件が合格しました。固定したTypeScript 5.9.3とVS Code 1.90 API型による `tsc` の型検査も合格しました。相互確認として、生成した新規文書をPython Core自身の `inspect` にかけ、wire v1の有効なコンテナー（1024×1024、カラータイプ6、ソース73バイト）として受け入れられることを確認しました。

## WebviewとMonacoの追加 — P2-02

## 遅延プレビューと手動切替 — P2-03

編集プレビューはPython Coreだけが生成します。`src/preview.ts` はフレームワークに依存しないコントローラーで、入力停止300ms後に描画し、スケジュールごとに世代を持ち、新しい編集がスケジュールされた後に終わった結果は破棄します。そのため、ワーカーの完了順序が逆転しても、常に最新の原文が優先します。`src/corePreview.ts` は、bridgeパッケージの `LatestValidation` レーンで編集原文を検証し、成功した場合にのみCoreの `build` コマンドで専用のプレビューファイルへ描画します。不正な原文は描画前に拒否され、表示されることは決してありません。プレビューファイルがユーザーの文書になることもありません。

プレビュー領域は、実際の保存済みrasterで開きます。「Saved PNG」と「Edited SVG」の切替は手動のみです。`webview/preview-state.js` はモードをトグルボタンからのみ変更し、プレビュー結果が届いても編集画像を更新するだけで、モードは決して切り替えません。自動の画像差分も自動切替もありません。

Coreへは新しい設定 `vectorPng.corePythonPath`（CoreをインストールしたPython 3.11〜3.13）経由で接続します。管理対象環境の統合が入るまでは、未設定の場合に編集プレビューが利用不可を報告し、保存済みプレビューは動作し続けます。

## 原文保持の保存と別名保存 — P2-04

プロバイダーは完全な `CustomEditorProvider` になりました。保存はバイトを直接書きません。`src/save.ts` が流れを統括し、`src/coreSave.ts` がbridge経由でCoreの `build` コマンドを実行します。その際、保存先の現在のSHA-256をリビジョントークンとして渡します。Coreはprofileを検証し、IHDRのviewportで描画し、候補を検証してから原子的に公開し、上書きされる元のバックアップスナップショットを保持します。profile違反は保存を禁止し、トークン取得後に保存先が変わっていれば競合となり、失敗した場合は元のファイルに一切触れず、プロバイダーが例外を投げるため、VS Codeはdirtyバッファを保持します。原文バイトは正確に保持されます。再直列化をしないため、BOM・CRLF・整形がそのまま残ります。別名保存は新規ファイルを作成するか、既存の保存先をそのファイル自身のトークンの下でのみ上書きします。取消はCore開始前に限り有効です。開始後はCoreの段階的公開が原子的であるため、保存が部分的なファイルを残すことはありません。

Revertはディスクから原文を読み直します。バックアップは現在のファイルに未保存の原文を持つ小さなサイドカーを添えてコピーし、hot-exit復元時に未保存の編集を保ったまま開き直せます。編集イベントは変更ごとに基本的なundo/redoクロージャ付きで発行します。権威あるundo/redo履歴同期はP2-05、外部変更の監視はP2-06です（保存時のトークン確認により、無言の上書きは既に防がれます）。

ローカルでの検証：実Coreありで拡張の単体テスト56件が合格しました（Coreなしでは50件合格、Core統合テスト6件はスキップ）。統合テストは実際のファイルシステム保存を検証します。BOM/CRLFの原文がバイト単位で往復し、バックアップスナップショットが残ること、不正な原文が禁止され元ファイルのハッシュが変わらないこと、古いトークンが競合となり外部版が保持されること、別名保存が元に触れず新規ファイルを書くことを確認しました。TypeScriptの型検査も合格しました。拡張ホストとパッケージ済みVSIXのテストはP3の受入作業として残るため、P2-04はその証跡が得られるまでオープンのままです。

## undo/redo同期と復旧 — P2-05

`src/history.ts` が、各文書の唯一の権威ある履歴になりました。Webviewの編集はそこへちょうど一度だけ記録されます。入力の burst は1秒以内なら1つのundo可能なエントリに合体し、置換のような離散的な編集は分離したままです。同一内容の再配信（ホスト同期がWebviewから戻ってくる反響）は何も記録せず、編集イベントも発行しません。これがMonaco・ホスト・VS Codeのundoスタック間のフィードバックループを防ぎます。`CustomDocumentEditEvent` のundo/redoクロージャは、履歴のポインタを動かして結果のスナップショットをWebviewへ同期するだけです。保存は履歴を消さないため、保存をまたぐundoで編集前の原文に戻り、redoで保存済み状態に戻ります。dirtyかどうかは常に、現在のスナップショットが保存済み原文と異なるかで決まります。Revertは履歴をディスク状態へリセットします。

文書あたり複数エディターパネルを有効化しました。1つのパネルでの原文変更は一度だけ記録され、同じ保護付き経路で他のパネルへ同期されます（全体スナップショット同期で、副パネルのカーソルは保持されません）。バックアップの永続化は `src/backup.ts` へ移しました。バックアップはファイルのバイトと、未保存・保存済み原文を持つJSONサイドカーをコピーし、復元時は未保存の編集をバイト単位で正確に保ち、復元状態を根とする新しい履歴で開き直します。

ローカルでの検証：実Coreありで拡張の単体テスト66件が合格しました（Coreなしでは60件合格、Core統合テスト6件はスキップ）。新しい履歴テストは、undo/redoの往復、反響の抑止、redo末尾の切り捨て、合体、保存をまたぐundo/redoのdirty判定、置換のステップ、リセットと上限を確認し、バックアップテストはバイト単位の往復と破損サイドカーの扱いを確認しました。TypeScriptの型検査も合格しました。実エディターでのキー操作レベルのundo/redoと複数パネルの挙動は拡張ホスト受入作業（P3）として残るため、P2-05はその証跡が得られるまでオープンのままです。

## 外部変更の競合 — P2-06

各文書が `ExternalChangeTracker`（`src/watch.ts`）を持つようになりました。エディターが最後に合意したファイルバイトのSHA-256を、開いた時・保存後・再読込後に保持します。文書自身のファイルに対するファイルシステム監視は、観測したディスク状態をタイミングではなく内容で分類します。そのため、自分自身の保存の反響は構造的に無視されます。cleanな文書への外部変更は、通常の受動検出を経て（未検証では決してなく）再読込されます。dirtyな文書への外部変更、読めない変更、dirtyな文書の下での削除は、バッファに一切触れず保持し、エディター内と警告メッセージでユーザーに通知し、文書を競合状態にします。

文書が競合状態の間、通常の保存は進めません。ディスクから再読込するか、外部変更を上書きするか、別名保存するかを明示的に尋ねます。そのため、ユーザーが決めるまで双方の版が残り、CLI編集がdirtyな原文を黙って上書きすることも、その逆もありません。再読込で解決した場合はディスク状態を採用します。上書きの場合は通常のトークン確認付き保存（P2-04）を通り、そのリビジョントークンが、観測と保存の間に着地した変更に対する第二の防衛線であり続けます。dirtyな文書の下でファイルを削除した場合、次の保存で保持されたバッファから再作成できます。改名は、旧パスにおける削除として観測されます。

ローカルでの検証：実Coreありで拡張の単体テスト74件が合格しました（Coreなしでは66件合格、Core統合テスト8件はスキップ）。新しいテストは、判断マトリクス全体（自分の保存の反響、cleanな再読込、dirtyな競合、読めない内容、削除と再作成、合意バイトが戻った場合の競合解消）に加え、Core CLI自身を外部エディターとする統合シナリオを確認します。dirtyなバッファがその編集を生き延び、明示的な上書きで保存できること、cleanな文書がその編集後に再読込され削除を観測することを含みます。TypeScriptの型検査も合格しました。実拡張ホストでの監視挙動はP3の受入作業として残るため、P2-06はその証跡が得られるまでオープンのままです。

## 通常PNGの表示モード — Issue #46

通常PNG（埋め込みSVGソースのない正常なPNG）を、例えば「Open With…」からカスタムエディターで開くと、従来は失敗していました。`openCustomDocument` が「no embedded SVG source」で拒否するため、ユーザーは画像ではなくエラーを受け取っていました。カスタムエディターは、このようなファイルを今後は表示モードで開きます。

表示モードの文書はソースを持ちません。何も抽出せず、SVGソースを捏造することもありません。`pendingSource` は未定義のままなので、保存経路には書き出すものがなく、文書がdirtyになることも決してありません。開いて閉じても、ディスク上のファイルはバイト単位で同一です。ファイル監視、編集履歴、外部変更トラッカー、Python Coreはいずれも設定されず、revertは無操作です。パネルは静的ページ（`src/webviewHtml.ts` の `buildViewHtml`）で、同じ制限的CSPのもとスクリプトを完全に無効化します。メタ行には「`<width> x <height> PNG — no embedded SVG source (view only)`」と表示され、ラスター画像自体が市松模様の中央に表示されます（`webview/editor.css` の `#view-pane`）。Monacoペインはなく、エラー通知も診断もありません。

## SVGを開くこととvector-png書き出し — Issue #47

カスタムエディターは通常の `.svg` ファイルも開くようになりました（セレクターに `*.svg` を同じビュータイプ・優先度 `option` で追加するため、既定のSVG体験は変わりません）。SVG文書はPNGの編集モデル（保留中／保存済みソース、undo/redo履歴、複数パネルの同期、バックアップサイドカーによる復旧、外部変更の追跡）を共有し、取得と永続化だけが種類ごとに異なります。ソースはファイル自体のUTF-8テキストであり、文書サイズはルートのwidth/height属性（無ければviewBox、それも無ければCoreの既定である1024x1024ビューポート）から、新規依存なしに `src/svgSource.ts` が解析します。保存は、Coreの再構築ではなく、PNG保存でCoreが強制するのと同じSHA-256リビジョン合意で守られたプレーンなUTF-8書き込みとして、テキストをバイト単位で正確に書き戻します（`src/svgSave.ts`）。表示がsafe-svg-v1検証で妨げられることは決してありません。診断はソースペインで助言的なものにとどまり、編集プレビューはソースをそのままwebviewの `<img>` で描画します。Coreのプレビュー経路は描画前にプロファイル検証を行うため、一般のSVGを表示できないからです。SVGマークアップがDOMに入ることはありません。

新しいコマンド `Vector PNG: Export as Vector PNG`（`vectorPng.exportAsVectorPng`。コマンドパレット、`.svg` のエクスプローラーコンテキスト、本エディター内のエディターコンテキスト）は、現在のソース（開いている文書の未保存を含むソース、未オープンのファイルについてはディスクの内容）を同名の `.png` へ書き出します。実働は `src/export.ts` が担い、本番依存は `src/coreExport.ts` にあります。ソースはCoreの `validate --profile safe-svg-v1` で検証されます。有効なソースはCoreの `build` コマンドで書き出され、保存経路のリビジョントークンの規律に従います（既存ターゲットはモーダルのOverwrite確認の後にだけ、その現在のSHA-256のもとで置換されます。通常PNGのターゲットも同じ確認の対象です）。無効なソースは何も書きません。構造化プロファイル診断（重大度、コード、要素、属性、行、列、メッセージ、提案）は、テキスト文書として開くShow diagnosticsアクション付きのエラー通知に出され、明示的なExport via normalizationの選択があった場合にのみ、Coreの `convert` コマンド（描画ゲート付き正規化とそれに続くbuild）が実行されます。`convert` は厳密に上書き禁止であるため、既存ターゲットは先に退避され、変換が失敗または例外となった場合は逐語的に復元されます。したがって、失敗した書き出しや辞退された書き出しが、部分的なPNGや置換されたPNGを残すことは決してありません。正規化書き出しが成功した後は、変換レポートのアクセシビリティ損失の警告が提示されます。ソースの `.svg` が書き出しによって変更されることは決してありません。`validate --profile` と `convert` はプロトコル1トランスポートでは表現できないため、ブリッジの規律を映した、境界付きでシェルを使わないスポーンによりCoreの版管理されたJSON CLI経由で実行されます。一方 `build` は保存とまったく同様にプロトコルランナーを再利用します。Python Coreの変更は不要でした。

## Normalize SVGコマンド — Issue #47 フォローオン

ユーザーの要望により、同じIssueで、開いている `.svg` 文書のソースをその正規化形で置き換える明示的なコマンド `Vector PNG: Normalize SVG`（`vectorPng.normalizeSvg`）を追加します。これは開く・保存・書き出しとは意図的に分離されています。本プロジェクトでは正規化は明示的な操作であり、自動的なステップには決してなりません。このコマンドは本エディター内の `.svg` 文書に対してのみ有効であり（アクティブなパネルから追跡する `vectorPng.documentIsSvg` コンテキストキーがパレットとエディターコンテキストの項目を制御し、エクスプローラーの項目は `.svg` ファイルを対象とします）、vector-png文書に対しては決して有効になりません。未オープンの `.svg` ファイルに対して起動された場合は、先にそのファイルをエディターで開いて文書に対して操作します。エディターの背後でファイルを書き換えることは決してありません。

Coreの `normalize` 操作は、文書の現在のソース（未保存の編集を含む）に対して実行され、その入力・出力・レポートは一時的な場所にのみ書かれます（`src/normalize.ts`、`src/coreNormalize.ts`）。Coreの操作にはsvg-normalization-v1の変換前後の描画ゲートが含まれるため、成功は、置き換えたソースとピクセル単位で同一に描画されることが保証されます。正規化されたテキストは、履歴機構を通じた通常の編集として適用されます。単一の、汚れた、取り消し可能な変更として着地し（1回のundoで正規化前のソースに戻ります）、保存は競合保護を備えた通常の保存フローを使います。変換レポートから引いた短い要約（実体化された宣言、展開されたマーカー、解決されたstyle要素とclass属性、アクセシビリティの移行）が続き、記録されたアクセシビリティの損失は別の警告で明示的に提示されます。正規化が無言で無損失に見えることは決してありません。出力が現在のソースとバイト単位で同一の場合、コマンドは文書がすでに正規化済みであると報告し、編集を行いません（汚れた状態も履歴エントリも生じません）。セクション7のいずれの失敗においても、文書は完全に手つかずのままとなり、失敗はそのコードとメッセージとともに表示され、レポートの構造化エラーは診断文書で利用できます。これは書き出しの検証失敗と同じ提示の規律です。

## macOSでの実機確認とプレビューステータスの修正 — Issue #58 フォローアップ

2026-10-30、ユーザーはマージ済みmainからビルドしたVSIX（SHA-256 5d7431810aaf59595a17b6b2bafbb1cd78d175fac9162cf0b3bd6fac61c243c2。インストール先の拡張機能本体のハッシュがVSIXと一致しました）を使い、macOSで切り替えたフローのVS Codeホスト実機確認を行いました。合格した項目：Pythonはどこにもありません。コマンドパレットにSet Up／Environment Status／Roll Backのコマンドは表示されず、設定検索では拡張機能の設定が見つからず、パッケージのコマンド定義と設定定義にもPython関連はありません。vector-pngを開くとEditingプレビューが表示され、FILLを編集して保存した後は、埋め込みのvector-png.svg iTXtに変更が含まれていました。Export Plain PNGは、埋め込みSVGチャンクを持たない64×64のPNGを出力しました。スタイルと角丸のあるSVGは正規化され（classとstyleが解決され、塗りと線が属性化されました）、vector-pngとして書き出すと（100×80）、画像には角丸と線が表示され、埋め込みSVGにはrx="14"と塗り・線の属性が残りました。これは移行前のゲートが拒否したCSS rxのクラスです。未実施が2点あります。旧ゲートが拒否したコーパスの実ファイル（確認の場では特定できず、角丸SVGは確認用に作成した独立サンプルでした）と、Pythonがまったく存在しない環境での実行です（このMacにはPythonと以前の管理環境があり、Pythonのセットアップは行っておらず、拡張機能のJavaScriptを検索してもPythonやchild_processへの参照は見当たりませんでしたが、それだけでは不在環境での実行を証明できません。その確認はUbuntuで計画しています）。

確認から所見が1つ出ました。vector-png文書で、ホスト起点の操作（確認ではFILLの編集と保存）の後、Editingプレビューの画像は更新されるのに、「Rendering the editing preview…」の表示が残る場面がありました。根本原因：webviewのリビジョンカウンタは自身のタイピング編集でのみ進み（ホスト更新は変更ハンドラを抑制して適用されます）、ステータスは、そのカウンタ以上のリビジョンでタグ付けされた描画が届いたときにだけ消えます（editedRevision >= revision）。しかしホストのonSourceSync購読は、同期描画をリビジョン-1でスケジュールしていました。そのため描画は画像を更新してもステータスは決して消えず（記録された編集リビジョンが後退することもありました）。修正：各パネルが、webviewから最後に報告されたリビジョンを追跡し（すべてのsourceChangedメッセージで更新します）、同期描画をそのリビジョンでスケジュールするようにしました。初期スケジュールも同じトラッカーを使います。プレビューコントローラの世代ガードが、より新しいタイピング編集に取って代わられたものを破棄するため、このタグはwebviewが表示しているソースの描画を正確に指します。拡張スイートの配線テストがこのタグ付けを固定しています（修正前のホストでは失敗します）。検証結果：拡張スイートはデフォルトで186/186、tscクリーン、ts-coreスイートは135/135（変更なし）です。
