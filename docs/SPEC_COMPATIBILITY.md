## Evidence boundaries

[Phase 0](PHASE0.md) records Windows/Python 3.13: 43 implementation tests and 10 pinned structural tests passed; 21 container probes plus 2 XML probes reveal the gaps above. [Raw probe results](../evidence/phase0-probes.json) deliberately retain accepted/rejected outcomes instead of calling them a conformance pass count. Unsafe SVG may be container-valid; preview equality is independent. Python 3.11/3.12, full OS support, extension-host behavior and all real-machine acceptance remain unverified. Optional upstream normalization is not automatically imported into this editor. Record every later change with spec sections, fixtures, results, compatibility impact and full English/Japanese updates.


Current writer scope (SPEC §§3–7): unchanged UTF-8 source in canonical compressed iTXt, IHDR viewport generation, validated candidate and exact local RGBA8 verification, explicit overwrite/backup and cooperative conflicts are implemented. Arbitrary external-writer races, crash durability and editor saves remain open; see [WRITING.md](WRITING.md). No wire/pin change or complete-conformance claim.

Bridge follow-up: protocol-1 stdin requests, inline exact source, strict bounded decoding, TypeScript orchestration/stale-result rejection and read-only environment health checks are implemented in 0.1.0.dev3. Details were recorded in the retired BRIDGE document. No file-format, renderer policy, specification pin or writer concurrency change; P1-04 native/transitive locking, graceful worker cancellation, bounded renderer output and upgrade/rollback remain open.

Native/artifact hashing, VS Code setup/dirty-edit integration and full renderer controls remain open. This does not change wire v1, the specification pin, the Core writer or default standalone pip dependency behavior.

safe-svg-v1 schema follow-up (Issue #22, SPEC §5): the profile was compared point for point with the Core and agrees on the whole allowlist surface (18 elements, 51 attributes, value/reference rules, limits). Evidence: SC-01 to SC-09, SC-11 and SC-12 in the Core suite. Phase 2 (Skill procedure in skills/vector-png/SKILL.md, Monaco consuming the generated metadata with content-model child completion) and SC-10 (end-to-end generate-validate-build-verify, including the never-overwrite-on-failure rule) are implemented; see [SAFE_SVG_V1.md](SAFE_SVG_V1.md).

P0 audit deepening follow-up (Issues #1/#2, SPEC §§2-4, 6-8): requirement-level probes were added for chunk ordering and APNG markers, unknown critical/ancillary chunks, keyword duplication across text chunk types, zlib stream integrity, language tags and translated keywords, limit error categories, palette/grayscale/Adam7 raster breadth, rebuild metadata non-retention, transparency exactness, external-reference rejection, timeout categorization and the inspect/verify claim separation (50 probes, all passing; see the dated section in [PHASE0.md](PHASE0.md)). svg-normalization-v1 import (Issue #48, normalization profile §§1-8 at the same pin 8238ebda): the Core now implements the experimental input-processing profile as the explicit commands `normalize input.svg output.svg --report report.json` and `convert input.svg output.png --report report.json` (also reachable through the protocol-1 JSON transport). Implemented: §2 input validation with the baseline limits; §3 closed CSS subset via a hand-written CSS tokenizer/parser (no blind semicolon splitting; tinycss2 is not a Core dependency); §3.1 restricted arrow-marker expansion; §4 cascade/inheritance with winning declarations materialized as presentation attributes and full safe-svg-v1 revalidation of the output; §5 accessibility migration with every removed role/aria-* attribute recorded with its target or loss reason; §6 before/after rendering gate in the existing bounded CairoSVG renderer under exact decoded RGBA equality, with staged no-clobber publication that never modifies the input; §7 conversion report with the profile's failure codes (invalid-xml, unsafe-input, unsupported-css, invalid-reference, resource-limit, output-exists, output-alias, render-error, render-mismatch); §8 convert path runs the normalization gate first, then the existing writer and container checks, recorded separately. The spec fixtures were vendored verbatim into packages/core/tests/fixtures/normalization with a provenance note: all 24 catalog cases pass with their expected failure codes, the synthetic nameplate output is byte-identical to nameplate.expected.svg, and its analysis-determined report fields match nameplate.expected-report.json. The Core suite gains 62 normalization tests (full suite: 245 passed, 1 skipped, Python 3.13). Corpus verification against the user's 9 real files (local evidence only, not committed): 6 files normalize successfully with the render gate passing; ce-marking-qr-nameplate.svg fails only on `letter-spacing` (unsupported-css; the property is absent from the §3 table and has no safe-svg-v1 attribute - spec gap G1 in makotosan/vector-png-spec#3); the two ISO 7010 files fail only on curved (C-segment) marker-end hosts (unsupported marker geometry - spec gap G2). Two interpretation choices are recorded: font-family words follow the profile text (an unquoted leading-hyphen name such as -apple-system and quoted names without a first-character restriction are accepted; the fixture tool's narrower pattern is not followed - spec gap G3), and the marker triangle's closepath accepts lowercase z, which is the identical command in SVG. Compatibility impact: safe-svg-v1 acceptance is unchanged everywhere (build/save/validate verdicts, SC-03, the allowlist), wire v1 and the specification pin are unchanged, and normalization runs only as this explicit import operation - never automatically on read, extraction or save. The earlier statement that upstream normalization "is not automatically imported into this editor" is superseded only in that deliberate, explicit sense. Finite fixtures and the 9-file corpus are evidence, not full conformance certification for arbitrary CSS-styled SVG.

svg-normalization-v1 amendment follow-up (Issues #48/#22, tracking makotosan/vector-png-spec#3): the editor-side implementation of the three spec amendments, which are being drafted in the specification repository in parallel; this change anticipates them and does not bump the pin. G1: `letter-spacing` added as a safe-svg-v1 presentation attribute ahead of the pin - Core allowlist 51 -> 52 attributes, the policy and the regenerated RNG/rules/Monaco/manifest artifacts, shared by `profile_check.py`, with the extension's mirrored profile data updated to match; the normalization section 3 table gains the property with the grammar "signed decimal, optionally px; the keyword `normal` is not accepted", materialized like the other properties and rendered by CairoSVG in the gate. G2: normalization section 3.1 host paths may use absolute C segments in addition to M/L/H/V (S/Q/T and all other commands remain rejected); the final tangent of a cubic segment is endpoint minus second control point, falling back to endpoint minus first control point when the former is zero, and zero in both is rejected as degenerate marker geometry; all other section 3.1 restrictions are unchanged. G3: no behavior change - the implementation already followed the profile text for font-family names; a pinning test now covers a list containing -apple-system and a double-quoted name. Affected spec sections: the safe-svg-v1 attribute list (G1), normalization section 3 (G1/G3) and section 3.1 (G2). Evidence: Core suite 255 passed, 1 skipped (Python 3.13; baseline before this change 245 passed, 1 skipped); the three new synthetic amendment cases (letter-spacing, curved-marker-host, font-family-system-names - same ids and inputs as the fixtures being added to the specification repository) accept, and `validate --profile safe-svg-v1` accepts a letter-spacing file while still rejecting class/style; extension suite 79 passed, 8 skipped, 0 failed with the regenerated Monaco metadata, TypeScript check clean.
